## Introduction
The worker executes tool calls that are dispatched by the server. To prevent a worker from running tool calls that were not authorized by a trusted client, every tool-execution request is signed by the client using an asymmetric key pair (End-to-End Authorization, or E2EA). The worker only accepts signed requests whose signer is present in its trust store of **trusted signers**.

A trusted signer consists of:
- **Signer ID**: a stable identifier for the client/device that produced the signature.
- **Public key (Base64)**: the public half of the client's signing key pair, used to verify signatures.
- **Permissions** (optional): a list of permission tokens that scope what the signer is allowed to authorize.

This guide explains how to register a client as a trusted signer on a worker.

## How to obtain a client's signer credentials
The signer ID and public key are generated by the client and never leave the device except when you explicitly copy them. To retrieve them:

1. Open the client application.
2. Go to **Settings → E2EA Security**.
3. Copy the **Signer ID** and the **Public Key (Base64)** values.

For convenience, the E2EA Security tab also shows a ready-to-use **Worker Registration Command** that already contains your signer ID and public key. You can copy that command directly and skip the manual substitution described below.

## Adding a trusted signer via the CLI
The worker provides a dedicated admin mode that adds or replaces a single trusted signer in `application.json` and then exits. It does **not** start the worker runtime, so it is safe to run against a running worker's config directory (the change takes effect on the worker's next start).

Run the worker with the `--add-trusted-signer` flag together with the required signer payload:

```bash
./start-worker.sh --add-trusted-signer \
  --signer-id=<SIGNER_ID> \
  --public-key-base64=<PUBLIC_KEY>
```

- `--add-trusted-signer` enables trusted-signer admin mode and exits before runtime bootstrap.
- `--signer-id` is **required** and must match the client's Signer ID exactly.
- `--public-key-base64` is **required** and must be the client's Base64-encoded public key.
- `--permissions` is **optional** (see [Permissions](#permissions)).

If a trusted signer with the same signer ID already exists, it is replaced in place rather than duplicated.

Example using the values from the E2EA Security tab:

```bash
./start-worker.sh --add-trusted-signer \
  --signer-id=client-desktop-7f3a \
  --public-key-base64=MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcD... \
  --permissions=mcp:read,mcp:write
```

### Docker deployments
When running the worker from the prebuilt Docker image, the startup script is `start-worker-docker.sh` (the `start-worker.sh` template shown in the client maps to this script inside the container). Pass the same flags as command arguments:

```bash
docker compose run --rm chatbot-worker --add-trusted-signer \
  --signer-id=<SIGNER_ID> \
  --public-key-base64=<PUBLIC_KEY> \
  --permissions=mcp:read,mcp:write
```

Or directly with `docker run`:

```bash
docker run --rm chatbot-worker:latest --add-trusted-signer \
  --signer-id=<SIGNER_ID> \
  --public-key-base64=<PUBLIC_KEY>
```

## Configuring trusted signers via environment variables
Trusted signers can also be supplied entirely through environment variables, which is useful for containerized or automated deployments. The worker maps environment variables to config keys via `env-mapping.json`. Each trusted signer occupies a numbered slot, and each permission is a separate variable:

| Environment variable | Config key | Description |
| --- | --- | --- |
| `WORKER_TRUSTED_SIGNER_1_ID` | `worker.trustedSigners[0].signerId` | Signer ID of the first trusted signer. |
| `WORKER_TRUSTED_SIGNER_1_PUBLIC_KEY_BASE64` | `worker.trustedSigners[0].publicKeyBase64` | Base64 public key of the first trusted signer. |
| `WORKER_TRUSTED_SIGNER_1_PERMISSION_1` | `worker.trustedSigners[0].permissions[0]` | First permission of the first trusted signer. |
| `WORKER_TRUSTED_SIGNER_1_PERMISSION_2` | `worker.trustedSigners[0].permissions[1]` | Second permission of the first trusted signer. |
| `WORKER_TRUSTED_SIGNER_2_ID` | `worker.trustedSigners[1].signerId` | Signer ID of the second trusted signer. |
| `WORKER_TRUSTED_SIGNER_2_PUBLIC_KEY_BASE64` | `worker.trustedSigners[1].publicKeyBase64` | Base64 public key of the second trusted signer. |
| `WORKER_TRUSTED_SIGNER_2_PERMISSION_1` | `worker.trustedSigners[1].permissions[0]` | First permission of the second trusted signer. |
| `WORKER_TRUSTED_SIGNER_2_PERMISSION_2` | `worker.trustedSigners[1].permissions[1]` | Second permission of the second trusted signer. |

Add the corresponding entries to `env-mapping.json` (the default mapping already defines two slots) and set the environment variables in your `docker-compose.yml` or container environment.

Example `docker-compose.yml` snippet:

```yaml
services:
  chatbot-worker:
    environment:
      - WORKER_TRUSTED_SIGNER_1_ID=client-desktop-7f3a
      - WORKER_TRUSTED_SIGNER_1_PUBLIC_KEY_BASE64=MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcD...
      - WORKER_TRUSTED_SIGNER_1_PERMISSION_1=mcp:read
      - WORKER_TRUSTED_SIGNER_1_PERMISSION_2=mcp:write
```

The resulting `application.json` structure (whether written by the CLI or assembled from env vars) looks like this:

```json
{
  "worker": {
    "trustedSigners": [
      {
        "signerId": "client-desktop-7f3a",
        "publicKeyBase64": "MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcD...",
        "permissions": ["mcp:read", "mcp:write"]
      }
    ]
  }
}
```

## Permissions
Permissions are free-form tokens that scope what a trusted signer is allowed to authorize. They are stored on the signer and returned by the worker after a successful signature verification; downstream authorization logic uses them to decide whether a given tool call may proceed.

- Permissions are supplied as a comma-separated list, e.g. `mcp:read,mcp:write`.
- Empty fragments and duplicate values are ignored; the remaining values are kept in first-seen order.
- If `--permissions` is omitted (or the env-var slots are empty), the signer is stored with an empty permission list.
- The example tokens `mcp:read` and `mcp:write` are used throughout the worker tests and represent read/write access to MCP tool execution. Use the tokens that match your deployment's authorization rules.

## Notes and limitations
- The `--signer-id`, `--public-key-base64`, and `--permissions` flags are only valid together with `--add-trusted-signer`. Using them without it is rejected at startup.
- The public key must be valid Base64 that decodes to at least one byte; otherwise the worker rejects the signer at startup (or when the CLI admin mode runs).
- Adding a trusted signer via the CLI writes to `application.json` in the resolved config directory. The change only takes effect when the worker (re)starts and reloads its configuration.
- A signer ID must be unique within the trust store. Re-adding the same signer ID replaces the existing entry, including its public key and permissions.
